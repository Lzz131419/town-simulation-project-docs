# 第6–9周交付讲解与文件展示指引

## 1. 开场：为什么重做（约40秒）
我们保留雾河镇“数字居民生活、公共决策和可复盘”的初衷，把产品愿景收敛为固定30+1人的MVP1。本次交付的是开发前的工程契约，旧HTML只是交互探针，不能代表正式功能完成。

## 2. 第6周：上下文（约50秒）
打开context.md，展示目标、范围、七类Non-Goals、技术约束与风险；打开agent-rules.md，说明AI修改白名单和证据要求。课程要求的看板与文档PR演练要展示真实线上记录，当前本地准备状态必须如实说明。

## 3. 第7周：Spec（约90秒）
打开scope，再打开M4。用119与120镇币的边界说明AC可判定：119拒绝且world/events不变，120执行后公库0、清水+30、信任+5、外部支出+120。五个模块各有故事、GWT、功能/非功能、异常和Non-Goals。

展示本轮cold-start-01记录及其实际状态，说明新会话只读一个Spec，不拿旧记录替代新规则。

## 4. 第8周：架构（约70秒）
打开architecture依赖图：UI→M1→领域/证据→共享契约，无反向调用。解释为何选择浏览器模块与JSON，而非先加后端。打开ADR-002，说明副本提交与失败诊断分离解决复现矛盾；探针只检验机制，团队仍需人工接受ADR。

## 5. 第9周：任务（约70秒）
打开mvp1-plan的八列表，展示12任务、AC绑定、负责人、依赖、15工作日关键路径。打开分支表和PR准入清单，说明真实Issue号发布后再填；GitHub Projects必须有五个状态列与实际卡片，不能把本地表当成线上看板。

## 6. 收尾（约30秒）
展示delivery-checklist与validation记录。区分“文档完成”“机制验证”“正式实现验收”“人工评审/线上流程”。下一步按任务逐项实现，不绕过Spec直接堆功能。

## 备用问答
- 为什么没接大模型？初始愿景允许调整技术；MVP1优先规则透明和可复现，模型服务作为MVP2候选。
- 为什么不用HTTP状态码？当前是本地函数API，稳定Result/error.code可验收，后续服务化需新ADR。
- 为什么失败不写世界事件？拒绝命令记独立诊断；否则会破坏“恢复前后等值”的契约。成功日结算内的缺货仍是世界事实。
- 如何保证真实历史可信？没有此承诺；规则是教学假设，不做真实社会预测。
