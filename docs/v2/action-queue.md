# 行动队列与有限计划

日期：2026-11-20；本地实现，未提交GitHub。对应V2-AC-22。

## 现在可以怎样玩

打开生活手册的配方图鉴，依次把“收获谷物”“烘焙面包”“吃面包”加入计划。在地图底部展开待执行队列，可调整顺序、删除步骤，再点击“执行这份计划”。居民会依次完成三步，并自动停下；如果先烘焙却没有谷物，会显示失败原因并暂停后续行动。

地点详情也能加入具体行动。加入只保存安排，不立即生产或扣材料，不替换当前任务，不修改已有队列的顺序。可以连续安排同一种行动，最多8个待执行步骤；当前行走任务不计入这8步。所有动作仍到达后检查材料、精力和背包容量，不提前锁定原料。

## 三种控制方式

| 方式 | 行为 | 完成或失败 |
| --- | --- | --- |
| 本人控制 `manual` | 点击行动立即接管；已有队列保持暂停 | 单次行动结束后等待安排 |
| 执行本轮 `plan` | 按保存的队列执行，也会继续当前已经开始的行动 | 全部完成自动转为本人控制；失败立即暂停剩余步骤 |
| 长期托管 `rules` | 先执行队列，之后使用个人备用规则 | 延续已有饥饿、恢复、生产和失败退避规则 |

“停止行动”仍清除当前任务和路径、切回本人控制，保留尚未开始的队列。已经从队列取出的失败或停止步骤不会自动回到队列；失败不扣物资和精力、不计完成数，玩家检查原因后自行重新加入。没有自动插入采集/休息或模型生成步骤，避免改变玩家明确安排。

退出登录后，`plan`会继续执行到完成或失败为止，`rules`继续原来的规则；两者都不产生新模型请求。服务器关闭时世界停走，重启接续，不补算现实离线时长。计划完成/暂停写入世界事件，可在生活记录里筛选。

## API 与一致性

- `POST /api/me/plan/append`：接收`actions`，在世界锁与事务内校验并追加。空列表、非法动作或合并超过8步被拒绝，不部分追加。仅修改登录居民。
- `POST /api/me/plan/edit`：接收`expected`和新的`actions`。两者先按领域规则规范化；只有当前队列与expected一致才写入。执行tick取走步骤、另一标签页追加或AI替换都会导致旧编辑被拒绝，返回中文“计划已变化，请同步后重试”。该项目沿用业务校验400响应。
- `PUT /api/me/control`：增加`plan`枚举。没有待执行或当前任务时拒绝启动空计划；主动启用会清除历史重试等待。`rules`和`manual`兼容。
- 旧`PUT /api/me/plan`保持整份替换语义，供已有调用方兼容；网页草稿保存改用带expected的新编辑接口。模型生成计划仍按现有流程整份保存；队列操作会取消该用户尚在进行的模型请求。

草稿与已保存队列分开。保存只提交点击时的副本；请求期间继续改草稿不会把尚未保存的内容误当成服务端基线。冲突时保留草稿，并由用户“同步”更新，不静默覆盖他人的新安排。

## 工程与边界

- `domain/plans.py`：纯队列校验及有限模式完成/失败转换，无网络调用。
- `domain/scheduler.py`：推进路径、执行任务，再进行完成或失败转换。
- `services/commands.py`、`api/world.py`：身份归属与事务编排。
- `PlanQueue.vue`、`usePlanQueue.ts`：地图上的可编辑队列。
- `useAgent.ts`：草稿基线与保存冲突检查。

没有增加数据库表或强制迁移，模式保存在既有世界JSON里。不会修改旧世界中居民的现有控制方式。没有实现批量自动推导制作链、任务依赖图或材料预订；玩家决定步骤与顺序。
