# 后端工程审查与整改

日期：2026-11-20。范围：FastAPI、世界运行时、领域输入、模型适配、数据库结构和工程验证。只修改本地项目，没有 GitHub 提交或外部部署。本轮未改前端视觉与玩法参数。

## 审查结论

本轮将阻塞读写、取消协调、结构迁移、健康检查和错误协议补成独立基础模块。当前适合继续演进为工程化的多人小镇服务，**仍是单进程权威世界，不是经过大规模压测的分布式游戏服务器**。原有增量广播、慢连接队列、领域服务和财务守恒机制继续保留。

## 已处理问题

| 优先级 | 发现的问题 | 处理与验证 |
| --- | --- | --- |
| 高 | 异步登录、个人资料、留言等流程直接执行同步数据库或密码计算，可能阻塞主事件循环 | 普通同步接口交给FastAPI工作线程；异步归档、模型配置、上下文和调用记录使用阻塞任务适配器。模拟慢密码计算时存活探针仍能响应 |
| 高 | 简单取消`to_thread`等待会让同步事务继续执行，而调用方可能提前释放世界锁 | `settled_thread`等待线程完成并记录取消；世界成功提交后发布状态，再传播取消。重复取消测试确认锁不会提前释放 |
| 高 | 时钟的连接校验在异常保护范围外，临时数据库故障可能永久终止世界循环 | 连接校验、离线收尾、tick提交纳入同一轮异常处理；失败记录指标，下轮重试。注入一次数据库异常后验证继续推进 |
| 高 | 原健康接口只能表示启动完成，不能发现世界任务已退出或数据库不可用 | 分开live与ready；ready检查数据库、任务存活、最近循环结果和成功tick时效；故障返回503并给出检查结果 |
| 高 | `create_all`无法管理存量库升级，也没有可审查的结构版本 | 引入Alembic：0001基线/旧表接管，0002九项索引；启动前迁移，提供一致性备份与副本演练脚本 |
| 高 | 模型调用记录创建过程中取消，可能遗留无实际请求的running记录 | 创建记录与冷却时间在短事务内提交；等待创建完成取得记录ID，再将取消写回；DNS及HTTP不占用数据库会话。测试确认取消记录落库且不发模型请求 |
| 中 | 模型可返回列表类型的动作名/物品名，引起TypeError；接口数量允许隐式转换 | 领域层先检查类型再进行集合查找，按动作约束参数；Pydantic数量与价格启用严格整数，拒绝布尔、浮点和数字字符串 |
| 中 | 数据库故障与未知异常缺少一致的响应，参数错误可能回显输入 | 统一detail/code/request_id，数据库不可用返回503；参数错误只列字段与错误类型；保留HTTP状态及认证响应头 |
| 中 | 留言与事件历史缺少一致的游标边界，常用筛选缺少索引 | 两接口限制每页1–100条，使用正数且不超过64位整数范围的before游标；消息继续按本人收发范围隔离 |
| 中 | 旧库已有部分索引时，重复迁移可能冲突 | 索引定义一致才接管；列、唯一性或条件不匹配即停止。测试部分索引恢复、冲突拒绝、索引降级后再升级 |
| 中 | 仅有通过数量，没有固定覆盖率门禁和schema差异检查 | 增加90%语句覆盖率门禁、XML报告、CI空库升级与Alembic check；CI配置已写入，远程执行尚未发生 |
| 低 | 恢复个人计划后活动文字可能还显示旧任务 | 恢复时同步设置等待新安排，保持资产与世界时间不回退 |

## 模块职责

- `bootstrap.py`：先升级数据库结构，再初始化缺少的固定成员和世界，再做世界JSON增量升级。
- `infrastructure/async_io.py`：同步任务执行与取消协调；不放业务规则。
- `infrastructure/migrations.py`及`backend/migrations/`：显式结构版本；不负责世界地图迁移。
- `infrastructure/http.py`：请求关联、错误转换和基础请求日志。
- `api/health.py`：存活/就绪探针，不触发模型调用。
- `ai/records.py`：短数据库事务，与模型HTTP适配解耦。
- `runtime.py`：继续作为单进程世界写入协调器；广播网络发送不在事务锁中等待。

没有引入与现有规模不匹配的微服务。世界写入仍串行，移出事件循环并不意味着可以任意并发修改共享世界。

## 数据升级证据

使用SQLite备份API获得一致性备份，再在第二份副本升级；没有直接复制运行中的WAL主文件。停服后又生成最终备份并重复演练，才升级真实库。

- 10张原有表的行数和内容SHA-256在升级前后全部一致，包括完整世界JSON与revision。
- 重复upgrade不改变数据；schema与SQLAlchemy模型一致；integrity_check与foreign_key_check通过。
- 真实库升级完成、时钟启动前再次核对所有旧行摘要一致。
- 本地服务启动后观察tick从14104到14105，地图版本3、12名居民、总资金2840。账户、归档、留言、模型配置与模型记录摘要仍与停服备份一致。
- 原数据库及密钥继续使用，备份在被Git忽略的`.local/schema-rehearsal-*`，路径记录于[迁移结果](evidence/backend-audit-migration.json)。

接管旧表只检查必要列和主键，不会自动修复任意人工变更的类型/约束；额外使用Alembic模型差异检查。索引版本可回退，基础表降级明确拒绝删除。未来有意转换业务数据的迁移应提供单独的数据校验器，不能套用“所有行原样不变”的断言。

## 下一阶段的明确边界

1. **世界存储仍为整块JSON。** 每次tick读取/复制/写回整个世界，订单历史也留在其中；应根据性能采样拆出居民、订单和历史，补事务一致性及兼容迁移后再替换。
2. **必须单worker。** 多进程时钟、锁和在线状态没有外部协调；不能简单增加Uvicorn worker。扩展需要世界所有权租约、跨实例消息和命令顺序设计。
3. **客户端重试不是通用幂等。** 订单交付已有业务保护，普通写接口尚无统一幂等键和结果缓存；数据库已经提交但响应丢失时，需要更完整的命令确认机制。
4. **线程取消不是驱动终止。** 为保证事务协调，启动超时和取消会等待底层同步工作收尾；数据库连接/锁等待有时限，但没有统一SQL语句执行截止时间。就绪只读探针超时后线程也可能稍后结束。
5. **真实PostgreSQL仍待验收。** 本轮验证SQLite和模型结构一致性，没有声称完成PostgreSQL迁移、备份恢复、容器运行或多实例压测。
6. **真实模型与长期运行仍待验证。** 当前接口适配及取消通过模拟测试；真实供应商、长时运行的数据增长、故障注入和容量指标需要独立验收。
