# M2 居民生活、生计与社交

- 文档版本：1.1
- 状态：待评审
- 模块编号：M2
- 主责角色：居民系统负责人
- 复核角色：数据与测试负责人
- 上游范围：[mvp1-scope.md](mvp1-scope.md)

## 1. 摘要

本模块把“居民”从展示对象变成每日参与工作和消费的行动主体。M2 负责精力、饥饿、口渴、个人余额、职业产出和关系变化，并把所有变化输出为可审计结果。MVP1 不使用模型生成行动或对话。

## 2. 用户故事

### US-1：完成一天的生活结算

作为观察者，我想看到居民工作和消费后的状态变化，以便理解库存与个人余额为何变化。

### US-2：在短缺下优先满足基本需求

作为观察者，我想看到粮食不足时居民如何改变行为，以便追踪危机的社会后果。

### US-3：参加低成本的社交或娱乐活动

作为观察者，我想看到居民在中央广场活动并改变关系，以便验证小镇不只有经济结算。

### US-4：查看个人行动依据

作为观察者，我想查看一名居民今天做了什么以及为什么，以便将结果与规则对应。

## 3. 验收标准

### US-1

**AC-01（正常）**

Given 第 2 天有一名精力和库存充足的农夫，When 执行日结算，Then 该居民产出场景配置规定数量的粮食、获得不超过可用公库的工资、精力下降，并生成一条包含产出与工资的行动事件。

**AC-02（正常）**

Given 一名居民的饥饿值达到进食阈值，且个人余额、市场库存和价格均满足条件，When 执行消费，Then 市场粮食减少 1、居民余额减少固定价格、镇公库增加相同金额，居民饥饿值按规则下降。

**AC-03（边界）**

Given 一名居民饥饿值恰好等于进食阈值，When 执行消费判断，Then 系统仍按达到阈值处理，不得因比较符号错误跳过购买。

### US-2

**AC-04（异常）**

Given 市场粮食为 0，When 高饥饿居民尝试购买，Then 粮食库存保持 0、余额和镇公库不变，并记录 `FOOD_OUT_OF_STOCK`。

**AC-05（异常）**

Given 市场有粮食但居民个人余额低于价格，When 尝试购买，Then 库存、余额和公库不变，并记录 `INSUFFICIENT_PERSONAL_FUNDS`。

**AC-06（边界）**

Given 居民饥饿值为 100，When 结算结束，Then 数值仍限制在 100，且居民被标记为饥饿状态。

### US-3

**AC-07（正常）**

Given 中央广场开放且两名居民当天均未参加社交活动，When 执行娱乐结算，Then 两名居民的关系值各增加固定值且不超过 100，并生成一条包含两名居民 ID 的广场活动事件。

**AC-08（边界）**

Given 两名居民关系值已经为 100，When 再次参加广场活动，Then 关系保持 100，不产生负向溢出。

**AC-09（异常）**

Given 中央广场关闭或容量为 0，When 系统选择娱乐活动，Then 居民改做休息，不产生关系变化，并记录 `FACILITY_UNAVAILABLE`。

### US-4

**AC-10（正常）**

Given 一名居民完成工作、消费或休息，When 创建者打开其详情，Then 页面显示行动名称、结果、精力、饥饿、余额和关联事件序号。

## 4. 功能需求

### FR-01 居民字段

每名居民至少包含：

```text
agentId
displayName
sourceType: generated | digitalPerson
jobCode
energy: 0..100
hunger: 0..100
waterNeed: 0..100
cash >= 0
relationships: map<agentId, { trust: 0..100, affinity: 0..100 }>
status: active | resting | hungry | blocked
lastAction
```

数字人物与规则居民使用同一结算接口，不因来源不同跳过工作、消费或投票。

### FR-02 职业与产出

MVP1 支持以下职业代码：

| 职业 | 主要产出或效果 |
| --- | --- |
| `farmer` | 粮食 |
| `fisher` | 粮食 |
| `gardener` | 粮食 |
| `carpenter` | 木材 |
| `builder` | 木材 |
| `merchant` | 集市运营，不直接增加库存 |
| `doctor` | 健康服务示例，不模拟疾病传播 |
| `teacher` | 公共教育示例，不模拟知识树 |
| `weaver` | 日用品示例，只产生事件 |
| `resident` | 基础劳动或休息 |

产出数量、精力和工资成本必须来自场景配置，不得硬编码在界面显示函数中。

### FR-03 日结算顺序

对每名居民按稳定 `agentId` 排序，依次执行：

1. 根据当前状态选择行动：进食、工作、社交、休闲或休息。
2. 校验行动要求的精力、设施和个人余额。
3. 结算产出或服务结果。
4. 结算工资、购买和库存转移。
5. 更新精力、饥饿、口渴、余额和关系。
6. 写入行动事件和失败原因。

结算结束后，所有 0—100 数值必须截断到合法范围，所有库存和余额不得为负数。

### FR-04 基本需求

- 每过一个模拟日，饥饿和口渴按配置增加，精力按行动成本减少。
- 食物消费只在饥饿达到阈值时触发。
- 清水消费只在口渴达到阈值时触发。
- 当食物或清水不足时，居民进入 `hungry` 或 `blocked` 状态，但不会在 MVP1 中死亡。
- 休息可以恢复精力，不产生产出或关系变化。

### FR-05 金钱与库存

- 居民工资来自镇公库，支付额不得超过公库可用余额。
- 集市购买形成“居民个人余额 → 镇公库”的转移。
- MVP1 只追踪上述资金和资源守恒关系，不模拟银行、贷款和利息。
- 工资金额不足时必须支付可用部分并记录 `WAGE_SHORTFALL`，不得产生负公库。

### FR-06 关系与娱乐

- 至少维护 `trust` 和 `affinity` 两类关系值。
- 中央广场每天提供有限数量的社交或娱乐活动。
- 参与者按稳定 ID 和固定种子选择，不得依赖对象遍历的偶然顺序。
- 关系变化必须附带来源事件，不允许只静默修改数值。

## 5. 非功能需求

- **数值安全**：所有库存、余额和关系值在每次结算后通过统一校验。
- **可复现性**：相同初始状态、种子和操作序列产生相同行动顺序和关系结果。
- **可解释性**：每条失败结果包含稳定错误标识，成功结果包含产出、消费或关系差值。
- **性能**：31 名居民的单个模拟日应在 1 秒内完成规则计算。
- **隐私**：数字人物的个人字段只通过 M3 白名单进入本模块。
- **界面无关**：M2 规则不得读取 DOM 或依赖页面文本。

## 6. 边界与异常

| 场景 | 预期行为 | 错误标识或结果 | 对应 AC |
| --- | --- | --- | --- |
| 库存为 0 | 购买失败，库存不变成负数 | `FOOD_OUT_OF_STOCK` | AC-04 |
| 个人余额不足 | 购买失败，三项状态不变 | `INSUFFICIENT_PERSONAL_FUNDS` | AC-05 |
| 公库不足以支付全额工资 | 支付可用部分并记录差额 | `WAGE_SHORTFALL` | AC-01 |
| 精力不足完成工作 | 改为休息或返回不可行动结果 | `ACTION_NOT_ENERGISED` | AC-10 |
| 设施关闭或容量为 0 | 不执行设施活动 | `FACILITY_UNAVAILABLE` | AC-09 |
| 关系值达到 100 | 保持在 100 | 成功，不允许溢出 | AC-08 |
| 饥饿或口渴值越界 | 截断到 0—100 | `NEED_VALUE_CLAMPED` | AC-06 |
| 居民未知职业代码 | 当日只执行居民基础行为并记录错误 | `UNKNOWN_JOB_CODE` | AC-10 |
| 同日重复消费或社交 | 第二次请求不执行 | `DAILY_ACTION_ALREADY_USED` | AC-07 |

## 7. Non-Goals

- 不实现 AI 对话、人格生成或自由文本行动规划。
- 不实现完整市场价格发现、议价、贷款、利息或金融资产。
- 不实现疾病传播、死亡、出生、婚育和代际继承。
- 不实现复杂职业培训、技能树或任务链。
- 不实现完整社交网络推荐、群体心理或情绪模型。
- 不把关系数值当作真实亲密关系或心理健康判断。
